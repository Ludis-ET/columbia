# cPanel deployment and 503 recovery

The application requires a Node.js host; uploading a Next build to static hosting
does not run the admin console or forms. The single
[build and deploy workflow](../.github/workflows/deploy.yml) replaces the separate
CI workflow. Pull requests build and test; pushes to main and manual runs on main
also deploy the tested artifact.

## Why the logged deployment failed

LiteSpeed's lsnode.js loads the startup file with require(). The previous
ES module server.js contained top-level await, causing ERR_REQUIRE_ASYNC_MODULE
and an immediate 503. The new server.js works in either module mode and loads
cpanel.cjs asynchronously without top-level await.

The other error, reading previewModeId from undefined, means the process did not
receive the expected prerender manifest. The old workflow and runner rewrote
Next's generated manifests with fixed preview keys and uploaded files into the
running build. The new pipeline preserves generated manifests and rejects
incomplete builds.

Next's standalone output includes the runtime dependencies and compiled
configuration. Do not run npm install in the deployed release or edit manifests.

## Configure cPanel once

In **Setup Node.js App**:

- Node.js: **22.x** (matching Actions).
- Mode: **Production**.
- Application root: **columbia**, matching /home/columbmq/columbia in the log.
- URL: **https://columbiacareafh.com**, with no subpath.
- Startup file: **server.js**.

Keep the .htaccess routing and Node executable path generated by cPanel. The
deployment does not replace them. Confirm they point at this application root
and the selected Node 22 environment, rather than a retired Node 20 environment.

The FTP account's directory must be the same application root. If it is already
restricted to columbia, leave FTP_SERVER_DIR unset. If it starts elsewhere, set
that variable to the relative directory containing this app. Never target the
account home or public_html by accident.

Keep runtime settings in cPanel's environment variables, or a private .env file
in the application root. The launcher reads .env.production.local, .env.local,
.env.production and .env in that precedence order. cPanel environment variables
take precedence over all files.

Runtime settings:

- NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY: use the same
  values as the GitHub build.
- NEXT_PUBLIC_SITE_URL is already embedded as https://columbiacareafh.com
  by the workflow; no extra GitHub secret is needed.
- NEXT_SERVER_ACTIONS_ENCRYPTION_KEY: if configured for the build, use that same
  value at runtime.
- SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASS and SMTP_FROM for SMTP,
  or RESEND_API_KEY and RESEND_FROM for Resend.
- OWNER_NOTIFICATION_EMAIL / STAKEHOLDER_EMAILS for notification recipients.
- TURNSTILE_SECRET_KEY if Turnstile is enabled. Configure its corresponding
  NEXT_PUBLIC_TURNSTILE_SITE_KEY in GitHub at build time too.

Do not set PORT unless your hosting provider instructs you to. The generated
server defaults to 3000 and LiteSpeed/Passenger handles the app listener. Binding
defaults to 0.0.0.0; CPANEL_BIND_HOST can override it if your provider requires it.

Remove obsolete duplicate .env files after migrating their needed settings into
cPanel, so they cannot silently supply stale credentials. The deployment leaves
existing env files, the root node_modules symlink, logs and .htaccess untouched.

| NEXT_SERVER_ACTIONS_ENCRYPTION_KEY   | Stable Server Actions encryption key |

You do not need to recreate these secrets or add any new ones for the standard
deployment. Their values still need to be current and valid.

NEXT_PUBLIC_SITE_URL is already set to https://columbiacareafh.com in the
workflow. **Do not add it as a GitHub secret.** It is a public website address.

SUPABASE_SERVICE_ROLE_KEY may already exist in GitHub, but this deployment does
not read it. It is not needed for the application or build.

SMTP, Resend and notification settings stay in the existing cPanel environment
variables or private .env files. You do not need to duplicate them in GitHub.
Keep the same NEXT_SERVER_ACTIONS_ENCRYPTION_KEY value in cPanel if a runtime
value is set there.

### Optional settings: leave unset for the standard setup

No repository variables are required when the FTP account opens directly in
the columbia application directory and the host supports explicit FTPS on
port 21 with a valid certificate.

Only change these if your hosting configuration requires it:

| Repository variable | Default                     | When to change it                                         |
| ------------------- | --------------------------- | --------------------------------------------------------- |
| FTP_PROTOCOL        | ftps                        | Set to ftp only if your host requires plain FTP           |
| FTP_PORT            | 21                          | If your host uses a different FTP control port            |
| FTP_SERVER_DIR      | .                           | If your FTP login opens outside the application directory |
| SITE_URL            | https://columbiacareafh.com | If the public domain changes                              |

FTPS checks the certificate chain and hostname on both the control and data
connections. HOST selects the network address. The workflow already sets the
public certificate identity FTP_TLS_SERVER_NAME to vesper.hostns.io, matching
the FTP certificate observed at this site's server. No new secret is needed.

If your provider changes the certificate name, override FTP_TLS_SERVER_NAME as
a repository variable with the hostname confirmed by the provider. When using
the deployer outside Actions, it verifies against HOST unless
FTP_TLS_SERVER_NAME is explicitly set.

This deployer does not support SFTP or implicit FTPS.

Turnstile is optional. Only if you enable it, configure its public
NEXT_PUBLIC_TURNSTILE_SITE_KEY in GitHub and private TURNSTILE_SECRET_KEY in
cPanel. Otherwise leave both unset; deployment does not require them.

Runtime credentials are not copied into build artifacts.

## Deployment and verification

1. Before building a production deployment, Actions checks the FTP TLS
   handshake, login and application directory without changing files.
2. Lint, unit tests and deployment regression tests must pass.
3. Actions builds with locked pnpm dependencies on Node 22, then typechecks.
4. Packaging copies standalone output, public files and .next/static. It
   preserves generated manifests and removes traced environment files.
5. A smoke check starts the isolated artifact through require(), matching
   LiteSpeed's loading method. It checks readiness, the homepage, a JavaScript
   asset, a CSS asset and the admin login page.
6. Actions uploads the artifact into releases/<commit>-<run>-<attempt>/.
   The running release is never overwritten.
7. After all files arrive, FTP rename replaces active-release.json. Only then
   is tmp/restart.txt replaced to request a restart.
8. Live verification requires the exact release and commit, HTTP 200, the
   homepage, JavaScript, CSS and login page. A green upload alone is insufficient.
9. If verification fails and a previous managed release exists, its pointer is
   restored, the app is restarted, and that release is checked. The workflow
   still fails so the bad deployment is visible.

The first migration from the old layout can briefly interrupt service while the
startup files change. FTP rename must support replacing an existing file.
cPanel/LiteSpeed must honor tmp/restart.txt; otherwise the health check fails and
you must use the cPanel Restart button or ask the host to enable restart detection.

Old releases are deliberately retained for rollback. Monitor disk usage and
remove old, inactive release directories in cPanel periodically, keeping the
directories referenced by active-release.json and previous-release.json. Old
root .next files can be archived after the first managed release is verified.

Checks are read-only. They do not submit inquiries, send mail, or prove that
Supabase auth, SMTP and CAPTCHA credentials are correct. Verify an actual admin
sign-in and a permitted tour inquiry separately after recovery.

## Fix an FTPS certificate hostname mismatch

If Actions reports CERTIFICATE_VERIFY_FAILED with a hostname mismatch, the FTP
server is presenting a certificate for a different DNS name than HOST.

For this site's FTP endpoint, the certificate name is vesper.hostns.io.
The updated workflow already configures that name for TLS verification while
keeping the existing HOST connection address. Commit and push the updated
workflow and deployer, then run the workflow from the new commit.

Do not change HOST to vesper.hostns.io solely because it appears in the
certificate: the two names resolved to different IP addresses during diagnosis.
Use HOST for the application server's address and FTP_TLS_SERVER_NAME for its
provider-confirmed certificate name. Credentials and certificate verification
remain protected; the deployer does not fall back to unverified TLS or plain FTP.

## Recover the current 503

1. Rotate the SMTP password and Supabase service-role credential previously
   embedded in deploy.yml, and replace the exposed fixed Server Actions key.
   Removing them from the current file does not remove Git history.
2. Keep the six existing GitHub secrets listed above. Confirm their values and
   the matching cPanel runtime settings; no new GitHub secrets are required.
3. Push these changes to main, or merge them and select **Actions > Build and
   deploy to cPanel > Run workflow** on main.
4. If the new release does not start, click **Restart** in Setup Node.js App.
   Confirm server.js and cpanel.cjs are in the app root, active-release.json
   references an existing release, and that release has node_modules, server.js,
   .next/BUILD_ID and .next/prerender-manifest.json.
5. Check the latest stderr.log entry. Node loader failures, unreadable files,
   disk quotas and incorrect app-root routing need to be fixed in cPanel.
6. Open /api/health. It must report status ok and the new release. Check the
   homepage and /admin/login, then verify sign-in and the tour form.

For a manual rollback after a managed release has been deployed, in the cPanel
terminal and correct application directory:

    cp previous-release.json active-release.json
    touch tmp/restart.txt

Then verify /api/health and the homepage. If restart.txt is not honored, use
cPanel's Restart button. The first managed release has no previous managed
release to roll back to.
